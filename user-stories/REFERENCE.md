# Catalogue reference

## Source baseline and scope

Source baseline: committed apps and catalogue inputs at Starter Examples `614a056b931e42f070eca67ed5af43bb5fa6a1d4`. Inventory covers four owned apps (`api`, `hypermedia`, `inertia-react`, `inertia-vue`), their routes, pages, controllers, validators, guards and tests, linked cookbooks, demo seeders and app/repository operator commands.

## Roles and boundaries

- **Application visitor/account owner:** registers, authenticates, manages their native account, joins teams and controls their own credentials.
- **Team member/editor/inviter:** acts with the Access Control membership and permission resolved for the account authenticated on that route.
- **Configured support operator:** account listed by the kit's Masquerade configuration; host `canMasquerade` policy and, for edit, `canEdit` must approve. The target's normal business permission still applies.
- **Soft-delete administrator:** existing account with `is_soft_delete_admin` set to true through a trusted database operation; route guard determines which account is checked.
- **App operator:** runs migrations, development server and optional demo seeder for one kit.
- **App maintainer:** makes shared app and cookbook changes in Starter Examples and validates affected committed apps.
- **Package maintainer:** changes package implementation and validates package-local consumers and contracts in that package repository.

Roles summarize actual config, route and policy checks; they do not imply a package-wide application role system. Host authentication, mail delivery, database, deployment, policy, scheduler and email environment values remain host-owned. Browser examples use Account Kit `createLogNotifications`: links go to the server log in development, and the apps refuse production boot until a host mailer is configured. The API adapter records notifications in process memory and logs proof links in development; production delivery requires a host integration. As supplied, none of these adapters sends real inbox email.

## Proof delivery boundary

The supplied adapters do not send real inbox email. Browser development runs use `createLogNotifications`, which puts proof URLs in the server output; its production mode refuses boot until the host replaces that integration. See the [Hypermedia configuration](../apps/hypermedia/config/account_kit.ts), [React configuration](../apps/inertia-react/config/account_kit.ts) and [Vue configuration](../apps/inertia-vue/config/account_kit.ts) for the actual notification selection and test seams.

The API [createNotify adapter](../apps/api/config/account_kit_notifications.ts) calls [notifications.send](../apps/api/app/services/account_kit_notifications.ts), which appends notices, including proof-link values, to process-memory `notifications.events`. In development it additionally logs those values. The array is application/test state, not an inbox or a durable delivery queue, and is not a public link-retrieval endpoint. Production API delivery needs a host notification integration.

Signup, reset, verification, email-change and invitation acknowledgements retain their actual UI wording; “sent” or “check your email” in that wording does not establish inbox delivery. In the supplied development examples obtain proof links from the server output; tests can inspect their configured notification records. Opening or submitting a proof link remains the separate token journey documented by its story.

The browser kits use registered Account Kit sessions. Their raw web guard supplies the sign-in handle and revision to the session revision check and verified-account middleware. Effective routes still resolve the target separately through Masquerade. The API combined example uses bearer-token authentication. The API test harness can select the session branch for account and team route tests, but that branch is not a supported mixed-transport host configuration. The API Masquerade sample business routes `/api/v1/masquerade/account` and `/api/v1/masquerade/sensitive` use `api_effective`; Masquerade controls authenticate the operator with the raw bearer guard. The API sample documents [reading the effective account](api/us-api-22-read-masquerade-sample.md) and [trying a sensitive action](api/us-api-23-try-sensitive-masquerade-action.md). In API access-token mode, Masquerade control routes require the `masquerade` token ability and unsafe requests enforce the current `X-Masquerade-Context`, including while idle; the sensitive-action story shows that its context comes from raw `GET /masquerade`, not the effective-identity read. Browser kits check context on unsafe effective requests, including while idle, but configure enforcement as `report`, so a mismatch is reported rather than refused solely for that reason. Browser kits keep the raw session credential with the actor; rendered forms carry context and host CSRF fields.

All four kits include Account Kit, Masquerade, Access Control and Soft Delete integration. Browser team routes and API access-token team routes resolve the effective account's membership and permission. API tests also cover a raw-`web` session route branch, which is not a supported mixed-transport host configuration. Account management, self-deletion and native logout use the raw account identity or Account Kit blocker where configured. Exact route differences and fields are in the individual stories.
